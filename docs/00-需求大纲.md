# BNDS 剧场灯光控制系统 · 需求大纲

> 版本 v0.1（待评审） · 目标控台 Avolites Tiger Touch V16
> 仓库：[bndsljr/BNDS-Tiger-Touch](https://github.com/bndsljr/BNDS-Tiger-Touch)

---

## 0. 结论速览

1. **五项需求全部技术可行**，无需越狱、无需改控台固件，全部走官方 WebAPI（HTTP 4430）。
2. 全量 **3705 个 API 页面**已抓取并建立本地语料库，逐条核对了签名。
   **不存在"仅宏可用"的方法** —— 整个 API 面均可远程 HTTP 调用。
3. 正面发现（决定了方案能成立）：
   - `Playbacks.StoreCue` / `CueList.CreateCueList` → **批量编光可编程**；
   - `SetList.*`（含 `NextTrack()`）→ **剧场走 cue 模型原生存在**，GO = `NextTrack()`；
   - `Palette.StoreCurrentPalette` / `Group.StoreGroup` / `Fixtures.PatchFixtures`
     → **素材与灯具配接都可编程**（连配接表都能离线生成）；
   - `Command.RunCommand` 通用后门 → 未被干净暴露的操作可用原生命令行语法兜底；
   - **排练即录制**（`Timecode.Record` + `AssignTimecode`）→ 跟着音乐按 GO，
     系统自动把真实时码烘焙进 cue，**零硬件实现精确卡点**。
4. 硬约束（决定了架构，动手前必须知道）：
   - 🔴 **cue 内的属性数值读不出来** —— 只能读元数据。`TrackingData.FetchItems` 返回 `Void`，
     Tracking View 对外部程序不可达。→ R2 的"内容级"分析必须改走离线 show 文件或外部抓包；
   - 🔴 **控台无文件上传/下载通道**，且**连"加载一个 show 文件"都没有 API**
     （无 `Show.OpenShow`/`SaveShow`/`Export`）→ 这是"加载预编 show"这一环的最大不确定性；
   - 🔴 **WebAPI 无法注入时码或节拍**（`AcwTimecodeSource` 无 LTC/MTC/网络成员）
     → 帧级卡点必须引入 API 之外的硬件/MIDI 通道；
   - **句柄分组名字符串未文档化** → 必须运行时自省后缓存，不可硬编码；
   - **本机是 macOS，Avolites 官方模拟器为 Windows 专属** → 必须自建模拟器才能离线开发。
5. 最大的设计自由度在需求④「音乐卡点」的路线选择（见 §6.1），
   **建议优先拍板**，因为它决定是否需要采购/引入硬件，返工成本最高。

## 1. 项目背景与目标

### 1.1 场景
学校剧场，演出频繁（戏剧、音乐会、晚会、典礼）。现有 Tiger Touch V16 控台。
痛点推断（待确认）：
- 编光只能在控台面板上做，一次演出要预先耗大量时间在台面上点；
- 重复性的"变光"操作多，但缺乏可复用的模板；
- 音乐类演出需要人工跟着拍子按 GO，容易错拍；
- 已有 show 里的程序越攒越多，没人清楚里面到底有什么、哪些能复用。

### 1.2 总体目标
在 PC 上构建一套**编光 / 分析 / 演出 / 灌入**的完整工具链，
把"在控台上手工点"变成"在电脑上描述 + 批量生成 + 联机微调"。

### 1.3 非目标（明确划出，避免范围蔓延）
- ❌ 不替代控台做实时 DMX 输出（演出中控台仍是唯一输出源，安全兜底）；
- ❌ 不追求 1:1 复刻 Tiger Touch 的完整 UI；
- ❌ 不做灯具库/灯位（R20 等）的图形化建模编辑器（v1 不做，v2 视需要）。

## 2. 需求拆解（可验收条目）

### R1 · 电脑端快捷编光
| # | 需求 | 验收标准 |
|---|---|---|
| R1.1 | 在 PC 上定义"灯位/编组/颜色/位置/图形"等可复用素材 | 用文本（YAML/JSON）描述即可生成，无需碰控台 |
| R1.2 | 批量生成调色板与编组 | 一条命令创建 N 个调色板 + 编组，含 legend 命名 |
| R1.3 | 常用剧场状态的模板库 | 如"全台面光 / 侧光 / 天幕 / 追光位 / 谢幕"，一键生成 |
| R1.4 | 展开/对齐等"好看"的工具可编程 | 支持 Fan（曲线/分段）、Align、GroupOrder |
| R1.5 | 盲编，不影响当前演出输出 | 编辑期间台上输出不变（`Programmer.SetBlind`） |
| R1.6 | 整套操作可撤销 | 一次批量操作 = 一步撤销（`History.CreateThreadToken`） |

### R2 · Agent 分析已有程序
> ⚠️ **本节范围已按调研结果修正。** 调研**确认**：**无法通过 API 读出 cue 内的实际属性数值**（详见 §9.1）。
> 因此 R2 拆成两层，交付预期需相应调整。

**R2-A 层（纯 HTTP 即可，无障碍 —— 建议作为第一阶段交付）**
| # | 需求 | 验收标准 |
|---|---|---|
| R2.1a | 导出 show 的**结构与元数据** | 灯具表、句柄清单、playback 清单、cue 列表（cue 号 / legend / fade / delay / link / tracking 模式）、调色板与编组清单 |
| R2.2a | Agent 做**结构体检** | 输出：命名不一致、cue 编号断档、走 cue 表缺场次、重复命名、未使用的调色板/编组、时间设置异常 |
| R2.3a | Agent 生成 **cue sheet / 提示本** | 自动生成中文走 cue 表文档（含 cue 备注） |
| R2.4a | 分析结果可回写 | 建议可一键应用（需 R1.5 盲编 + 事务保护） |

**R2-B 层（需要 show 文件通道或外部抓包，成本高得多）**
| # | 需求 | 验收标准 |
|---|---|---|
| R2.1b | 解析 show 文件取得**数值级内容** | 离线解析 XML（`Show.LoadShow.ForceLoadXML` 证明 show 由 XML 支撑） |
| R2.2b | Agent 做**内容体检** | 输出：色温/亮度不合理、重复 look、场景间跳变过大、位姿冲突 |
| R2.3b | 运行时旁路采集 | 演出中抓 DMX/sACN，建立「cue ↔ 实际输出」对照表 |

> **R2-B 是否投入取决于两件事**：能否拿到 show 文件（§9.2）、XML schema 是否可解（❓ 未文档化）。
> **建议先交付 R2-A 的价值，R2-B 作为第二阶段目标。**
>
> ⚠️ 另有一个**操作副作用**必须计入设计：逐 cue 读取时间/legend 需要循环调用
> `Playbacks.TimesEdit.CueNumber` → `FillTimes(handle)` → 读属性，
> 复杂度 O(cues)，且**会移动控台操作员的时间编辑器选中项**。
> → 分析功能应限制在非演出时段运行，或先保存并恢复 UI 状态。

## 3. 技术调研结论（Titan 16 WebAPI）

### 3.1 传输层（已核实）
| 项 | 值 |
|---|---|
| 端口 | **4430** |
| 基路径 | `/titan/` |
| 读属性 | `GET /titan/get/2/<Provider>/<Property>` |
| 写属性 | `POST /titan/set/2/<Provider>/<Property>`（body 为裸值） |
| 调方法 | `GET /titan/script/2/<Provider>/<Method>?params` |
| 句柄发现 | `GET /titan/handles[/<Group>[/<page>]]` |
| 返回 | JSON |

统计（对 3705 页实测）：用 `/script/2/` 的 **2475** 页，用 `/script/`（无 2）的 **0** 页，
无 HTTP 示例的 **28** 页且**全是枚举/类型定义**。

**特殊参数类型**：`level=`（覆盖）、`levelDelta=`（增量）、`titanId=`、`userNumber=`；
句柄三种寻址 `handle_titanId=` / `handle_userNumber=` / `handle_location=`。

### 3.3 值得单独记住的五个"杠杆点"

**(1) `Command.RunCommand` —— 通用后门**
```
GET /titan/script/2/Command/RunCommand?command=<Titan 命令行语法>
```
可直接下发如 `1 THRU 10 @ 50 ENTER`、`RECORD CUE 1 ENTER` 这样的原生命令行。
凡未被 API 干净暴露的操作都能兜底，且实现成本远低于拼装几十个细粒度调用。
配套 `Command.AppendString` / `AppendUserNumber` / `AtVisible` / `CommandLineText` / `Backspace`
可增量构造命令。**这应该是编光层的默认实现手段之一，不是最后手段。**
（`Command.AppendStringAndPreview` 的文档注明：追加后若命令非法会被拒绝。）

**(2) `SetList` 就是剧场模型本体**
Set List → Tracks（每场/每曲一个）→ 每个 track 绑页面 + 宏 + 备注；GO 即 `NextTrack()`。
`CreateSetListFromPages` 能把整页内容一键聚合成走 cue 表 —— 这是"快捷变光"的批量原语。
`SetList.AddNote` 让 **cue 备注可编程**（对生成提示本极有价值）。

**(3) `script/` 端点会在响应体里返回值** ✅
`UserMacros.ExportXml(macroId)` 的签名就是 `String` 返回，文档明说
*"Returns a string with the exported macro in xml format"*。
→ `Int32`/`IEnumerable`/`String` 返回值的脚本方法**确实可被外部程序取用**
（例如 `Playbacks.GetPlaybackCueIds` 直接拿回 cue ID 列表）。
⚠️ 但**响应体的线格式（JSON？XML？带引号？）全语料未文档化**，须连真控台实测。

**(4) `UserMacros.ImportXml` / `ExportXml` —— 唯一的结构化双向通道**
整个 API 里**唯一**能收发结构化数据的通道（其余全是"文件路径"）。
→ 批量生成的推荐 payload 通道：PC 侧数据 → 生成 Titan 宏 XML → `ImportXml` 推入。
⚠️ 宏 XML 的 schema 在**另一本 Avolites 宏参考手册**里，不在本 API 文档范围内。

**(5) 批量 legend 的安全写法**
`Playbacks.SetCueLegend(handle, cueNumber, newLegend)` —— 显式寻址、**无上下文依赖**，
是批量写 cue 名称最安全的方式（对比 `Playbacks.Editor.Times.*` 依赖当前上下文，
且会改动操作者 UI 状态）。

### 3.4 关键枚举（已实测确认）
- `AcwTimecodeSource`：None / Internal / UsbExpert / Winamp / System / **Smpte**
- `AcwFrameRate`：Fps24 / Fps25 / Fps29DF / Fps30 / Fps44 / Fps60 / Fps100 / Fps1000
- `TimelineTriggerTypes`：Playback / WaitForGo / FadeToLevel / GoToCue / Preload / Flash / Swop / Marker
- `RequestInfo`（报告元素）：Fixtures / PlaybackMemories / PlaybackChases / **PlaybackCueLists** / **Timelines** / **Palettes** / **Groups** / All
- `AcwTrackingType`：Global / Track / Block / Solo / CueOnly / Individual / SoloEffects / BlockEffects

## 4. 系统架构

### 4.1 分层
```
┌──────────────────────────────────────────────────┐
│  UI 层     桌面界面 / CLI / 脚本                  │
├──────────────────────────────────────────────────┤
│  编排层    cue-engine(变光)  sync-engine(卡点)    │
│            injector(批量灌入)  analyst(agent 分析) │
├──────────────────────────────────────────────────┤
│  模型层    Show Model（灯具/编组/调色板/cue/时间线）│
│            + 预编程描述语言(YAML) → 编译为调用计划  │
├──────────────────────────────────────────────────┤
│  传输层    titan-client  （统一 API SDK / 重试/事务）│
├──────────────────────────────────────────────────┤
│  目标层    真控台 :4430   |   titan-sim（自建模拟器）│
└──────────────────────────────────────────────────┘
```

### 4.2 三种运行模式（同一套上层代码）
| 模式 | 目标 | 用途 |
|---|---|---|
| offline | 无目标，只建模 + 校验 | 排练前在家编 |
| sim | titan-sim 本地模拟器 | 开发/CI/教学，**本机必需的开发姿势** |
| live | 真控台 `http://<ip>:4430` | 现场联机 |

> 架构上必须是**适配器**：上层永远不感知自己连的是谁。
> 这是 R5.1「完全离线可编」和 R6.2「可测试」的共同前提。

### 4.3 统一寻址策略（重要）
- 内部引用**一律用 `titanId`**（连上控台后自省获得），不用字符串拼接的 `handle_location`；
- 首次连接执行一次**自省**：拉 `/titan/handles` → 反推合法分组名 → 缓存为本地配置；
- 提供「分组名映射表」配置层，固件/版本差异不改代码。

## 5. 模块分解

| 模块 | 职责 | 关键 API 依赖 |

## 6. 需要拍板的设计决策

### 6.1 ★ 音乐卡点走哪条路线（最高优先级）
> 🔴 **一个决定性前提**：**WebAPI 无法注入时码或节拍。**
> `AcwTimecodeSource` 只有 `{None, Internal, UsbExpert, Winamp, System, Smpte}` ——
> **没有 LTC / Art-Net / sACN / MTC 成员**。`Smpte` 是唯一的外部输入源。
> 因此「让 PC 把时码喂给控台」**必须依赖 API 之外的硬件或 MIDI 通道**。

| 路线 | 机制 | 精度 | 硬件需求 | 适用 |
|---|---|---|---|---|
| **A｜PC 生成时码，控台从属** | PC 从同一份音频生成 **LTC / MTC** 送入控台 SMPTE 或 MIDI 输入，控台按已写入的时码打 cue | 帧级（音画零抖动：音频与时码同源同钟） | **需要 LTC/MTC 编码器 + 到控台 SMPTE/MIDI 的物理通路**（MTC 可用虚拟 MIDI 口，成本低） | 严格卡点，**首选** |
| **B｜控台 `Internal` 计时器 + PC 驱动** | `SetTimecodeSource(id, Internal)` + `Timecode<X>.Play/Pause/Reset`；PC 对拍，并按时刻自己发 `NextStep` / `FirePlaybackAtLevel` | HTTP 往返，LAN 上典型 1–5ms，最差数十 ms | **无额外硬件** | 学校剧场足够，**推荐的零硬件方案** |
| **C｜PC 推 BPM 到速度主控** | `Masters.SetSpeed(bpmMasterHandle, bpm)` / `Masters.TapTempo`，playback 经 `HandleOptions.Playbacks.AssignSpeedSourceFromHandle` 绑定 | 不等于 cue 锁 | 无 | **仅用于效果**（chase/图形跟着节奏走），**不能保证某个 cue 落在某一拍** |
| **D｜控台内 Timeline + DAW 标记** | 标记从 DAW 导入，控台自己跑 | 帧级 | 需把标记文件放上控台 | 曲目固定、可预先排 |

**明确不要采用的两条**（调研已证否）：
- ❌ **Audio trigger 作主同步**：`threshold` 与 `useLevelMatching` 两个参数在文档中均标注
  **"Not Used"**，频段未枚举，且输入依赖物理 USB 面板；
- ❌ **BPM trigger 作主同步**：仅由 Pioneer DJ Tap 喂数据。

**建议组合**：**B 为主**（零硬件、可立即落地）+ **C 为辅**（让效果跟着节奏）。
若后期卡点精度不达标，再升级到 **A**（MTC 走虚拟 MIDI 口是成本最低的硬化路径）。
D 作为「曲目固定」的补充。

**★ 一个被低估的杀手级流程 —— 排练即录制（卡点）** ✅
```
POST /titan/script/2/Timecode/TimecodeOne/SetSource?source=Internal
POST /titan/script/2/Timecode/TimecodeOne/Play
POST /titan/set/2/Timecode/Record                        (true)
   每到一个音乐重音：
   POST /titan/script/2/CueLists/NextStep?handle_location=...
   POST /titan/script/2/Timecode/AssignTimecode?handle_location=...   ← 把「当前实时计时值」盖到下一步
POST /titan/set/2/Timecode/Record                        (false)
```
即：**放音乐，跟着重音按 GO，系统自动把真实时码烘焙进 cue。**
排练一遍就得到一份带精确时码的 cue list —— 全程 HTTP，无需额外硬件。
这可能是本需求最实用的落地方式。

**其他重要发现**：
- ★ `Timelines.CreateOrUpdateMarker(handle, externalId, time, legend)`
  —— **幂等 upsert，专为外部生产者设计**。
  比 `ImportMarkers` 更可靠：后者的 CSV 格式**完全未文档化**
  （全语料中零命中 Reaper/Ableton/Logic/Cubase/Pro Tools）。
  → **DAW「卡点」标记应走 CreateOrUpdateMarker，而非猜 CSV 格式。**
- `Triggers.AddSAcnTrigger` / `AddMidiTrigger` 是**文档完备的远程节拍注入**通道
  （走网络，不需控台硬件）。
- `PioneerDJ.BindDeckToMaster(deckId, AcwMaster)`（Master=8, LayerA=6, LayerB=7）
  —— 从 CDJ 取真实 BPM/节拍。
- 微调工具：`Playbacks.Editor.Timecode.Add/Subtract(offset)` 与 `TimecodeOffset`
  → 「把整首歌挪 2 帧」有现成 API。
- ⚠️ `TimecodeTime` 的 `time={}` **线格式未文档化**（全语料零个时码字面量）
  → 需用 `Timecode/MakeTimecodeTime` 探测，或读一个手工做的 cue 反推。

### 6.2 批量灌入走哪条路线
> ⚠️ 调研澄清：`ShowImport` 是 **show → show** 传输引擎，
> **不是** CSV/XML 通用导入器；且**没有** `Show.OpenShow` / `SaveShow` / `Export`。
> 加载预编 show 是整个方案最薄弱的一环。

- **路线 B（纯 API 重放）为默认** —— 不依赖文件通道、可逐项校验、可事务回滚；
- **路线 A（`ShowImport`）作高速铺量通道** —— 前提是能把 show 文件放上控台（USB/网络共享）；
- 路线 C（整体替换 show）通常不可接受（会覆盖学校控台现有 show）。

### 6.3 其他待定
- 桌面 UI 形态：独立窗口应用（Tauri）vs 浏览器访问的本地服务 vs 纯 CLI？
- 是否需要在演出中让 PC 承担关键路径？（若需要必须设计断连降级：已触发的 fade 应能自行走完）
- 卡点精度目标定多少？（决定停在路线 B 还是升级到 A）
- **现场是否有可用的 MIDI 接口或虚拟 MIDI 通路？**（决定路线 A 的成本）

## 9. 风险与对策

### 9.1 🔴 高（已确认，非猜测）：cue 内的实际属性数值**读不出来**
调研已**穷举确认**：不存在任何从 cue 读取属性/DMX 数值的方法
（无 `GetValue` / `GetAttribute` / `GetDmx` / `GetCueValues` / `Cue.GetContents`）。
更关键的是 **`TrackingData.FetchItems(TrackingDataItemsInView)` 返回 `Void`** ——
它把数据推进一个客户端对象，**没有 HTTP 形态的接收方式**，
即 Titan 中信息最丰富的 Tracking View **对外部程序完全不可达**。

能读到的只有：cue ID/句柄、cue 是否存在、live/next cue 号、
以及逐 cue 的 legend / fade / delay / link / **tracking 模式**（模式可读，数值不可读）。

**影响**：R2 的"agent 深度分析"**不能**做到「这个 cue 色温偏了」这类内容判断。

对策（按优先级）：
1. **先把 R2-A 层（结构/元数据体检）做扎实**，这部分无障碍且有真实价值；
2. 内容级分析改走**离线 show 文件解析** —— `Show.LoadShow.ForceLoadXML` 证明 show 由 XML 支撑，
   这是唯一真正能取到数值的路径，但属**文件级**能力且 schema 未文档化（❓）；
3. 或走**运行时旁路采集**：演出中抓 DMX/sACN，建立「cue ↔ 实际输出」对照表；
4. `Reports.GenerateReport` 可作为结构导出的补充，但注意
   `format` 取值（`ExportType` 枚举**文档中不存在**）与「报告落在控台侧文件而非 HTTP 响应体」两个限制。

### 9.2 🔴 高（已确认）：控台侧无文件上传/下载通道
控台所有批量数据能力都吃**控台本地文件路径**
（`ShowImport` 的 `AcwPathDeviceKey`、`Timelines.ImportMarkers` 的 `csvFilePath`、
`Reports.SelectDevice(devicePath)`），而**全 API 没有文件上传/下载 endpoint**。

进一步地，**连「加载一个 show 文件」都没有 API**：
不存在 `Show.OpenShow` / `Show.LoadShow(name)` / `Show.SaveShow` / `Show.Export*`。
`Show.LoadShow.*` 只是三个**偏好开关**；加载需要通过菜单/UI 层触发，
而具体如何触达**文档未说明**。

对策：
- 确认能否挂网络共享（`Show.CurrentPath` 含 deviceId，暗示存在网络设备概念）；
- 否则接受 U 盘等人工环节，并把它写进操作流程；
- 关注 `Titan.SyncNow()`（Titan 主从同步），可能是绕过文件通道的路径；
- **这会直接影响 §6.2 的路线选择，且是「加载预编 show」这一环的最大不确定性。**

### 9.3 ⚠ 高：本机无法离线仿真，也没有控台
本机 macOS，`/Applications` 无 Avolites 安装，`127.0.0.1:4430` 无响应。
Avolites 官方 PC 套件/模拟器为 Windows 专属。
对策：**M2 titan-sim 是必需项而非可选项** —— 它同时是开发环境、CI 基础和教学工具。

### 9.4 中：句柄分组名字符串未文档化（可解）
全语料中**不存在任何 `group=` 字面量取值**；`handle_location` 唯一示例是 `playback_2_1`
（小写单数，与 `Handles` 示例的大写复数 `Colours`/`Fixtures` 不一致）。
最佳证据是 `HandleOptions.<Group>.*` 的路径段：
`Chases / CueLists / Groups / Handles / LayoutElements / Layouts / Masters / Memories /
Palettes / PlaybackGroups / PlaybackShapes / Playbacks / SteppedPlaybacks / Timelines`。

对策（**不要硬编码**）：
`Handles.GetGroup(handle)` 可回读真实分组名字符串；
`Playbacks.IsAllowedGroup(groupName)` 可在录制前**校验**候选名。
→ 先用确定无误的寻址（`handle_titanId` / `handle_userNumber`）拿到句柄，
回读分组名，此后一律用该字面量。见 §4.3。

### 9.5 中：无认证机制（安全）
按文档，API 在局域网上无鉴权，任何能访问 4430 的人都可完全控制演出。
（`AuthorCredentials.*` 并非登录机制 —— 它是以具名作者身份写菜单属性。）
对策：演出网络隔离；本工具不在演出期间无人值守地暴露端口。

### 9.6 中：版本/型号差异与功能授权
文档是 16.0，介绍页却举例返回 "14.0"。Tiger Touch 的 Titan 版本、
以及 timecode / timeline 等功能是否分级授权或需 license，
**须现场确认** —— 若不支持，R4 整块需求都要改方案。

### 9.7 🔴 高（已确认）：WebAPI 无法注入时码或节拍
`AcwTimecodeSource` = `{None, Internal, UsbExpert, Winamp, System, Smpte}`，
**没有 LTC / Art-Net / sACN / MTC 成员**。`Smpte` 是唯一外部输入源。

**影响**：若要把卡点做到帧级（路线 A），**必须引入 API 之外的通道**：
LTC 编码器 + 音频接口，或 MTC（可走虚拟 MIDI 口，成本最低）。

对策：先按路线 B（零硬件、HTTP 驱动控台 `Internal` 计时器）落地，
把精度需求量化后再决定是否投入路线 A 的硬件。
**不要**把主同步建立在 audio trigger（`threshold` 参数文档标注 "Not Used"）
或 BPM trigger（仅由 Pioneer DJ Tap 喂数据）之上。

### 9.8 中：`TimecodeTime` 线格式未文档化
`time={}` 的取值格式在全语料中**零个字面量示例**。
对策：用 `Timecode/MakeTimecodeTime` 探测，
或先手工在控台做一个带时码的 cue，再 `GET .../Playbacks/Editor/Timecode/CueTimecode` 反推。
