## 0. v0.2 变更摘要

用户已就 v0.1 的开放问题作出决定，本版据此重写：

| 项 | v0.1 设想 | **v0.2 定案** |
|---|---|---|
| cue 内容可读性 | 待实测 | **接受不可读**，agent 分析只做结构/元数据层 |
| 文件上传/下载通道 | 待实测 | **不需要**，不作为设计前提 |
| 时码注入 | 三条路线待选 | **MIDI 线**（用户提供硬件），系统输出时码 |
| R3 变光模型 | Set List 走 cue 表 | **「散的 cue」** —— 单 cue playback 库，**不做 cue list** |
| R4 卡点驱动 | 控台从属为主 | **系统自身是播放引擎**：点播放 → 音乐与推 cue 同源同步 |
| 交互形态 | 未定 | **WebUI**，逻辑须清晰 |
| 控台接入时机 | 尽早 | **稍后经网线接入**，先以自建模拟器开发 |

### 三条已接受的 API 硬约束
1. **cue 内属性数值读不出来** —— 只能读元数据（cue 号 / legend / 时间 / link / tracking 模式）。
   已确认 `TrackingData.FetchItems` 返回 `Void`，Tracking View 对程序不可达。
2. **无文件上传/下载通道** —— 用户明确不需要，不纳入设计。
3. **WebAPI 无法注入时码/节拍** —— 由 **MIDI 线**补足（见 §6.1）。

### 🔴 v0.2 新增的两条「可能推翻前提」的发现

**① 控台身份未确认 —— v16 可能装不上（最高优先级）**
厂方文档：*"version 16 and above will not work on the Pearl Expert, **original Tiger Touch**,
Tiger Touch Pro or the **first version of the Tiger Touch II**"*；受影响机型含
**Tiger Touch II 序列 2001–3065**，最高只能到 **V15.1**。
15.0 与 16.0 的 API 有 **187 页差异**。

> **行动项**：拿到控台**序列号** + `GET /titan/get/2/System/SoftwareVersion`。
> 原版 Tiger Touch / TT Pro / 早期 TT II → 本项目的 API 面须改为 **15.x**。
> 客户端必须**记录实际版本并在不匹配时明确报错**。

**② WebAPI 是「另一个用户」，有它自己的 programmer**
社区原文：*"the web API runs headless, with its own programmer and UI…
**any functions which work with the programmer cannot be used in a meaningful way**"*、
*"the Web API is **regarded another user** by Titan. Hence, fixture selection done on
the console does not apply here."*

→ **该 API 擅长「操作/回放」，不擅长「编程」。**
⚠️ 此说法可能源自较早版本，且语料确实暴露完整 `Programmer` provider（321 页）——
**真相须实测**。但架构上必须容忍。

**对本项目的直接后果（重要）**：
| 能力 | 依赖 programmer | 可靠性 | 对应需求 |
|---|---|---|---|
| 触发/熄灭散 cue、音乐卡点推 cue | ❌ | **高** | **R3.3 / R4** |
| 读 show 结构、批量设电平/legend/页面 | ❌ | **高** | R2 / R3.2 |
| 从 programmer 录入新散 cue | ✅ | ⚠️ 待实测 | R3.5 |
| 批量生成调色板/编组/场景 | ✅ | ⚠️ 待实测 | R1.2 / R1.3 |

> **架构决策：把「操作/回放」作为可靠核心先做扎实；
> 「编程」类能力按待验证处理，并保证其受限时系统仍完整可用。**
> 这恰好与用户的真实诉求一致 —— 用户要的核心是
> **「点播放 → 同时把散的 cue 推起来」**，那属于 operate 侧，不受此限制影响。

## 1. 背景与目标

### 1.1 场景
学校剧场，演出频繁。现有 Avolites Tiger Touch V16 控台。
编光耗时、变光靠手工、音乐类演出需人工跟拍按键、已有 show 内容无人清楚。

### 1.2 总体目标
在 PC 上构建一套 **编光 / 分析 / 演出 / 灌入** 的一体化系统，
通过 **WebUI** 完成全部操作，把「在控台上手工点」变成「在电脑上描述 + 批量生成 + 联机运行」。

### 1.3 核心思路（v0.2 定案）
> **系统本身就是一个播放引擎。**
> 点「开始播放」→ 系统播放音乐，并由**同一个时钟**按时间表推动控台上的散 cue。
> 同时，散 cue 也**始终保持可人工实时干预**——人在系统或控台上随时能推。

### 1.4 非目标
- ❌ 不替代控台做实时 DMX 输出（演出中控台仍是唯一输出源，安全兜底）
- ❌ 不 1:1 复刻 Tiger Touch 界面
- ❌ **不做 cue list / 走 cue 表**（用户明确要求散 cue）
- ❌ 不做 R20 灯位图形化建模（v1）

## 2. 需求拆解（可验收条目）

### R1 · 电脑端快捷编光
| # | 需求 | 验收标准 |
|---|---|---|
| R1.1 | 用文本描述生成素材 | YAML/JSON 描述 → 生成编组、调色板、场景，无需碰控台 |
| R1.2 | 批量生成调色板与编组 | 一条命令创建 N 个，含 legend 命名 |
| R1.3 | 剧场状态模板库 | 「全台面光 / 侧光 / 天幕 / 追光位 / 谢幕」等开箱可用 |
| R1.4 | 展开/对齐等观感工具可编程 | Fan（曲线/分段）、Align、GroupOrder |
| R1.5 | 盲编，不影响当前输出 | 编辑期间台上输出不变 |
| R1.6 | 整套操作可撤销 | 一次批量 = 一步撤销（`History.CreateThreadToken`） |

### R2 · Agent 分析已有程序（**仅结构层**）
| # | 需求 | 验收标准 |
|---|---|---|
| R2.1 | 读出现有 show 的结构与元数据 | 灯具表、句柄清单、playback 清单、cue 号/legend/时间/link/tracking 模式、调色板与编组清单 |
| R2.2 | 结构体检 | 命名不一致、编号断档、重复命名、未使用素材、时间设置异常 |
| R2.3 | 生成提示本 | 自动生成中文 cue sheet / 操作提示文档 |
| R2.4 | 建议可回写 | 一键应用（受 R1.5 盲编 + R1.6 事务保护） |

> ⚠️ **内容级分析（如"这个 cue 色温偏了"）在本 API 下不可能实现**，用户已接受。
> 这决定了 R2 的交付边界：**只做结构与元数据**。

### R3 · 剧场快捷变光系统 —— **散的 cue 库**
| # | 需求 | 验收标准 |
|---|---|---|
| R3.1 | **每个变光状态 = 一个独立 playback** | 单 cue memory，**不组成 cue list** |
| R3.2 | 散 cue 库可视化 = 「变光台」 | WebUI 上一屏看到全部状态，显示名称/页码/状态 |
| R3.3 | 可**人工实时推** | 人在 WebUI 或控台上随时触发/熄灭任一 cue，互不干扰 |
| R3.4 | 变光带时间 | 每个 cue 的 fade in/out/delay 可设定 |
| R3.5 | 从控台现状反向录入 | 能把控台 programmer 当前状态存成新散 cue（含读取现有字幕） |
| R3.6 | 散 cue 可编组/分页 | 按场景（第一幕/第二幕）或用途（面光/侧光/特殊）组织页 |
| R3.7 | 批量下发 | 一次把整个散 cue 库灌入控台 |
| R3.8 | 可撤销 | 与 R1.6 共用事务机制 |

### R4 · 演出系统：音乐卡点（**系统作播放引擎**）
| # | 需求 | 验收标准 |
|---|---|---|
| R4.1 | 系统播放音乐 | 在 WebUI 里选曲目并播放（本地音频文件） |
| R4.2 | 同一时钟推 cue | 点「开始播放」→ 音乐与推 cue 由**同一时钟**驱动，不靠两套时基 |
| R4.3 | cue 表按时间戳绑定 | 每首歌一张表：`时刻 → 目标散 cue → 电平 / fade` |

| R4.5 | 人工干预不打架 | 播放中随时人工推/收任一 cue，系统不反向覆盖 |

| R4.8 | 暂停/继续/跳转 | 播放控制与 cue 调度同步响应 |
| R4.9 | 断连安全 | 系统掉线时控台侧不失控，已触发的 fade 自行走完 |

## 3. 技术基础

### 3.1 传输层（已核实）
| 项 | 值 |
|---|---|
| 端口 | **4430** |
| 读属性 | `GET /titan/get/2/<Provider>/<Property>` |
| 写属性 | `POST /titan/set/2/<Provider>/<Property>` |
| 调方法 | `GET /titan/script/2/<Provider>/<Method>?params` |
| `/2/` 前缀 | **强制**（1203/1203，零例外） |

> ⚠️ 官方 Introduction 页是过时的 Titan 14 材料，**不可作为协议依据**。详见调研笔记 §2。

### 3.2 「散的 cue」在 Titan 中的落点 ✅
| 动作 | API |
|---|---|
| 记录一个散 cue（从 programmer） | `Playbacks.StoreCue(group, index, updateOnly)` |
| 触发到指定电平 | `Playbacks.FirePlaybackAtLevel(handle, level, alwaysRefire)` |
| 熄灭 | `Playbacks.KillPlayback(handle)` / `ReleasePlayback` |
| 设电平 | `Playbacks.SetPlaybackLevel` |
| 批量 legend | **`Playbacks.SetCueLegend(handle, cueNumber, newLegend)`**（显式寻址、无上下文依赖） |
| 单 cue playback 配置 | `HandleOptions.Memories.*`（`FixtureOverlap`、`FadeOut`、`CurveList`） |
| 全部熄灭 | `Playbacks.KillAllPlaybacks` |

> 单 cue playback 就是 Titan 的 **Memory**；`HandleOptions.Memories.*` 是其配置面，
> 与 `HandleOptions.CueLists.*` 并列 —— 印证散 cue 与 cue list 是两条独立路径。

### 3.3 需求 → API 能力矩阵（摘要）
| 需求 | 核心 API | 状态 |
|---|---|---|
| R1.2 调色板/编组 | `Palette.QuickCreatePalette`、`Group.QuickCreateGroup`、`Palette.StoreCurrentPalette`（须先 `CurrentPaletteNumber` → `SyncProperties`） | ✅ |
| R1.4 展开/对齐 | `Programmer.Editor.Fixtures.Fan.*`、`AlignSelection.*` | ✅ |
| R1.5 盲编 | `Programmer.SetBlind(enabled, setChangesLive, fadeTime, fixtureOverlap)` + `BlindActive` | ✅ 无头可用 |
| R1.6 撤销 | `History.CreateThreadToken` / `Undo` / `GotoTransaction` | ✅ |
| R2 结构导出 | `Playbacks.GetPlaybackCueIds`、`DoesCueExist`、`Playbacks.TimesEdit.FillTimes` + `Playbacks/Editor/Times/*` | ✅ O(cues) 且改 UI 状态 |
| R3 散 cue | 见 §3.2 | ✅ |
| R4 推 cue | `FirePlaybackAtLevel` / `SetPlaybackLevel` / `KillPlayback` | ✅ |
| R4 时码 | `Timecode.SetCueTimecode`、`Timecode.Record`、`Timecode.AvailableSources` | ✅ 但注入需 MIDI |
| R5 批量灌入 | 纯 API 重放：`PatchFixtures` + `QuickCreateGroup` + `QuickCreatePalette` + `StoreCue` | ✅ 全远程 |
| R5 配接 | `Patch.FixtureManufacturers/FixtureNames/FixtureModes` + `Fixtures.PatchFixtures` | ✅ |
| — 通用后门 | `Command.RunCommand(command)` | ✅ |
| — **cue 内容数值读取** | — | 🔴 **不存在**（已接受） |
| — 时码/节拍注入 | — | 🔴 **API 无**，走 MIDI |

### 3.4 必须知道的实现陷阱
- **`handle_location` 不可用** —— 全语料唯一示例 `playback_2_1` 是生成器硬编码、
  被复制到 419 处（甚至泄漏成 `palette_location=playback_2_1`）。
  **一律用 `titanId`**，次选 `userNumber`。
- **427 个方法「URL 存在但参数构造不出来」**（`={}` 空花括号）。
  每个几乎都有「有类型兄弟」：`Palette.CreatePresetPalettes` → **`Palette.QuickCreatePalette`**；
  `Group.CreateAutoGroup` → **`Group.QuickCreateGroup`**。客户端需内置替代映射表。
- **`Attribute.*`（207 页）全是 `Attribute.Mask.*`**（属性掩码），不是属性元数据；
  且**拿不到数值范围**。
- **无逐灯具属性写入器** —— `SetControlValue*` 作用于整个选中集；
  手写 fan 只能是 O(n) 循环，优先用 `FanControlValueById(value_leveldelta=…)`。
- **`Palette` 与 `Palettes` 是两个 provider**，后者全是 `Palettes.Editor.*`（第三个并行编辑上下文）。
- `{titanId}` 只是「任何 `Int32`」的渲染形式，不代表值是 ID。
- `AcwUserNumber` 无字面量示例（43 处占位符），按普通整数处理但需实测。

完整清单见 `docs/01-API调研笔记.md`。

## 4. 系统架构

### 4.1 分层
```
┌─────────────────────────────────────────────────────────┐
│  WebUI（浏览器）  准备 · 演出 · 复盘 三大域               │
├─────────────────────────────────────────────────────────┤
│  应用服务层（Node）                                      │
│   REST/SSE API  ·  静态资源  ·  会话与状态推送            │
├─────────────────────────────────────────────────────────┤
│  核心引擎                                                │
│   散cue库(cuebank)  演出时钟(showclock)  调度(scheduler) │
│   编光生成(compiler)  分析(analyst)  灌入(injector)      │
│   时码输出(MTC/LTC via MIDI)                             │
├─────────────────────────────────────────────────────────┤
│  模型层   Show Model ＋ YAML 描述 → 调用计划              │
├─────────────────────────────────────────────────────────┤
│  titan-client  统一 API SDK（寻址/编码/重试/事务/替代映射）│
├─────────────────────────────────────────────────────────┤
│  目标层   真控台 :4430   │   titan-sim（自建模拟器）      │
└─────────────────────────────────────────────────────────┘
```

### 4.2 三种运行模式（同一套上层代码）
| 模式 | 目标 | 用途 |
|---|---|---|
| `offline` | 无目标，只建模与校验 | 纯离线准备 |
| `sim` | 内置 `titan-sim` | **控台接入前的主要工作方式**；开发/CI/教学 |
| `live` | 真控台 `http://<ip>:4430` | 现场联机 |

> 适配器模式：上层永远不感知连的是谁。这是 R5.1 与 R7.2 的共同前提。

### 4.3 演出时钟模型（R4 的关键设计）
```
浏览器音频 (HTML5 Audio)  ──报告 position──►  服务端 showclock
                                                    │  单一单调时钟（锚定 + 漂移校正）
                                                    ▼
                                              scheduler
                                                    │  到时刻
                                                    ▼
                                        titan-client ──► 控台 FirePlaybackAtLevel
```
- **音频在浏览器播放**（音质、用户手势授权、无需服务端音频驱动）
- **时钟与调度在服务端**（精度、可测、可断言）
- 浏览器周期回报 `currentTime` 做**漂移校正**，使「观众听到的」与「推 cue 的时刻」同源
- 人工干预走**独立通道**，不经过 scheduler，因此不会被系统反向覆盖（R4.5）

## 5. 模块分解

| 模块 | 职责 | 关键依赖 |
|---|---|---|
| **M1 titan-client** | API SDK：URL 构造、参数编码、**替代方法映射**、重试、事务包裹、错误规范化 | 全部 |
| **M2 titan-sim** | 自建控台模拟器：实现本项目用到的 API 子集 + 有状态 show 模型（含散 cue、programmer、playback 电平） | — |
| **M3 show-model** | 领域模型 + YAML 预编程语言 → 调用计划编译器 | — |
| **M4 cuebank** | **散的 cue 库**：定义/命名/分页/生成/录入/批量下发 | `Playbacks.StoreCue`、`SetCueLegend`、`HandleOptions.Memories.*` |
| **M5 showclock** | 演出时钟：音频锚定、漂移校正、暂停/跳转 | — |
| **M6 scheduler** | 卡点调度：cue 表解析、到时刻推 cue、命中统计 | `Playbacks.FirePlaybackAtLevel` |
| **M7 timecode** | MIDI 时码输出（MTC/LTC）与控台从属方案 | 需 MIDI 硬件 |
| **M8 analyst** | 现有 show 结构导出 + 体检 + 提示本生成 | `Playbacks.GetPlaybackCueIds`、`Playbacks/Editor/Times/*` |
| **M9 injector** | 批量灌入：规划 → diff 预演 → 执行 → 校验 → 回滚 | 纯 API 重放链路 |
| **M10 webserver** | 应用服务：REST/SSE、静态资源、会话 | — |
| **M11 webui** | 浏览器界面（准备/演出/复盘） | M10 |

**技术栈**：TypeScript + Node 24（本机已有 v24.16.0）+ pnpm 10.33。
理由：跨平台（macOS 开发 → 现场可跑）、HTTP 密集场景顺手、类型可对 API 建模、前后端同语言。
UI 用轻量原生前端（无框架或极轻框架），理由：**演出页对稳定性与启动速度敏感**，
不希望引入庞大构建链；后续视需要再升级。

### 5.1 WebUI 信息架构（R6.2「逻辑清晰」的具体化）
按 **准备 → 演出 → 复盘** 三域划分，不混页：

| 域 | 页面 | 内容 |
|---|---|---|
| **准备** | ① 连接 | 控台 IP、连接状态、自省结果（分组名/灯具/页面） |
| | ② 灯具与编组 | 配接表、编组、灯具状态 |
| | ③ 变光台编辑器 | **散 cue 库**：新增/命名/分页/排序、从 programmer 录入、从控台反读 |
| | ④ 音乐卡点表 | 曲目 + 时间戳列表，绑到散 cue；边听边标 |
| | ⑤ 批量灌入 | 计划 diff → 确认 → 执行 → 回滚 |
| **演出** | ⑥ 演出台 | **大按钮散 cue 触发面板** + 播放控制 + 时钟/命中状态 |
| | ⑦ 卡点监看 | 时间轴进度、即将触发的 cue、实际命中偏差 |
| **复盘** | ⑧ 分析报告 | show 结构体检、命名/编号问题、提示本导出 |
| | ⑨ 日志 | 本次演出的 cue 触发记录与偏差统计 |

> 设计原则：**演出域不出现任何会改变数据结构的按钮**；
> 所有编辑操作都在准备域，避免演出中误操作。

## 6. 已拍板的设计决策

### 6.1 ★ 音乐卡点方案（定案）
**主方案：系统自持时钟 + 同时推 cue**
- 系统在浏览器播放音乐，服务端用同一时钟调度推 cue（R4.2）
- 掌控台走 `FirePlaybackAtLevel`，不依赖控台时间线
- 精度目标 ≤ ±20ms（LAN 内 HTTP 往返实测 1–5ms 典型，余量充足）

**辅方案：MIDI 时码（用户已确定使用 MIDI 线）**
- 系统经 MIDI 输出 **MTC**，控台设为从属（`Timecode.SetTimecodeSource`）
- 用途：需要帧级精度、或希望**控台侧也能独立跟时码跑**的场合
- ⚠️ 已知：`AcwTimecodeSource` 枚举未列 MTC，但存在 `Timecode.Midi.*`
  （`EnableGlitchDetect` / `GlitchTimeout` / `GlitchTolerance`）→ **需实测确认**
- 兜底：若 MTC 不通，改用 **SMPTE/LTC**（`Smpte` 是枚举中唯一外部输入源），
  需音频接口输出 LTC

**明确不采用**
- ❌ Audio trigger 作主同步 —— `threshold` 与 `useLevelMatching` 文档均标注 **"Not Used"**，
  频段未枚举，输入依赖物理 USB 面板
- ❌ BPM trigger 作主同步 —— 仅由 Pioneer DJ Tap 喂数据
- ❌ **cue list / 走 cue 表** —— 用户明确要求散 cue

### 6.2 批量灌入方案（定案）
- **纯 API 重放为唯一路线**（用户不需要文件通道）
  `PatchFixtures` → `QuickCreateGroup` → `QuickCreatePalette` → `StoreCue` → `SetCueLegend` → `HandleOptions.Memories.*`
- 全程包在 `History.CreateThreadToken` 事务里，失败即 `Undo`
- 不涉及 `ShowImport` / show 文件加载（因无文件通道，且非必需）

### 6.3 其他
- **不做 cue list**（R3 定案）
- cue 内容数值分析**不做**（已接受 API 限制）
- 控台接入前一律以 `titan-sim` 开发；接入后仅切换目标地址

## 7. 数据模型草案

```
Production（一场演出/一个 show 的本地镜像）
├── Fixtures[]        灯具：manufacturer/model/mode/dmxAddress/userNumber, titanId?
├── Groups[]          编组：名称、成员、顺序
├── Palettes[]        调色板：类型、引用、legend
│
├── CueBank           ★ 散 cue 库（核心）
│   └── ScatteredCue[]  每个 = 一个独立 playback
│       ├── id / name / legend
│       ├── page, index        控台落位
│       ├── look               灯具属性集合（生成 programmer 用）
│       ├── times              fadeIn / fadeOut / delay
│       ├── level              默认触发电平
│       └── tags[]             场景归属（第一幕 / 面光 / 特殊…）
│
├── Songs[]           曲目
│   └── Song
│       ├── audioPath / duration
│       ├── offsetMs           整曲微调
│       └── CueMark[]          卡点：{ tMs, targets: [cueId], level, fadeMs, note }
│
└── ShowMeta          控台版本、分组名映射、页面规划
```

## 8. 实施路线图

| 里程碑 | 内容 | 交付物 | 可控台? |
|---|---|---|---|
| **M0 调研定稿** | v0.2 评审通过 | 本文档 | — |
| **M1 通路** | `titan-client` + `titan-sim`。**内置修正**：`_levelDelta` 大写 D、显式句柄后缀、18 个分组名、`HH:MM:SS:FF`、替代方法映射表 | 可跑通的自省脚本 + 测试 | 否 |
| **M2 服务与界面骨架** | webserver(SSE) + WebUI「准备域」基础：连接/灯具/句柄浏览 | 浏览器里能看到 sim 的状态 | 否 |
| **M3 ★ 演出台（核心价值）** | showclock + scheduler + 散 cue 触发面板 + 播放控制 | **浏览器点播放 → sim 上散 cue 按时触发** | 否 |
| **M4 变光台编辑器** | 散 cue 库：定义/命名/分页/生成（**依赖 programmer，需实测**） | 可编辑并下发散 cue 库 | 否（部分待实测） |
| **M5 音乐卡点表** | 曲目 + 时间戳绑定 + 边听边标 + 偏移微调 | 一首歌完整卡点 | 否 |
| **M6 现场联机** ⚠ | 接真控台：**先验 §10.1 清单**（版本/序列号优先），再首次实灌 | 未知项清零 + 剧场跑通一次 | **是** |
| **M7 分析与提示本** | analyst + 复盘域 | WebUI 复盘页 | 是 |
| **M8 时码（MIDI）** | MTC/LTC 输出，控台从属 | 帧级卡点兜底 | 是 |

**关键排序理由**
1. **M1–M5 完全不依赖控台**，可在本机把系统做到「能演示、能彩排」的程度；
2. **M3 刻意排在 M4 之前** —— 因为 WebAPI 是「另一个用户」，
   **operate/replay（推 cue）可靠，program（编光）待验证**。
   先把不依赖 programmer 的核心价值做出来，风险最低、交付最快，
   且正是用户最想要的「点播放 → 推散 cue」；
3. **M6 是风险关口**，把未知项攒成一次现场批次；
4. **M8 时码排在最后** —— 主方案不依赖它，它是精度兜底而非地基。

## 9. 风险与对策

### 9.1 🔴 cue 内容数值不可读（已接受，影响 R2 边界）
只做结构/元数据体检。**不要承诺「AI 帮你看灯光对不对」**。

### 9.2 🔴 无文件通道（已接受，不影响方案）
批量灌入全程走 API 重放，不依赖文件。

### 9.3 🔴 时码注入需 MIDI 硬件（用户已提供 MIDI 线）
主方案（系统自持时钟）**不依赖**时码，因此即使 MIDI 方案受阻也不阻塞演出。
需实测：MTC 是否被 Titan 接受为时码源（枚举未列，但有 `Timecode.Midi.*`）。

### 9.4 ⚠ 本机无法用官方模拟器
macOS；Avolites 官方套件/模拟器为 Windows 专属；`127.0.0.1:4430` 无响应。
→ **M2 `titan-sim` 是必需项**，不是可选项。

### 9.5 ⚠ 句柄分组名未文档化
运行时用 `Handles.GetGroup` 回读 + `Playbacks.IsAllowedGroup` 校验，配置化映射表。

### 9.6 ⚠ 无认证机制（安全）
API 在局域网无鉴权 → 演出网络隔离；本系统不在演出期间暴露到不可信网络。

### 9.7 ⚠ 427 个方法参数构造不出来
客户端内置「阻塞 → 替代」映射表，开发期即时报错提示替代方法。

### 9.8 ⚠ 版本/功能授权
需现场确认 Titan 版本与 timecode 等功能是否授权。

### 9.9 ⚠ 人工与系统同时推 cue 的冲突
R4.5 要求人工干预不被反向覆盖。
→ 设计：人工操作走独立通道；系统只在**卡点时刻**发 `FirePlaybackAtLevel`，
不做全局状态轮询纠偏；必要时提供「系统托管/人工接管」显式切换。

### 9.10 ⚠ HTTP 抖动
主方案精度受 HTTP 往返与 OS 调度影响（LAN 典型 1–5ms，最差数十 ms）。
→ 用「控台侧 fade 时间」吸收；不足时升级 M8 时码方案。
